PROJECT OVERVIEW
================================================================================
Implement a custom Payroll Entry controller in spotledger_hr app that properly
handles salary components with Receivable/Payable account types by creating
journal entries with appropriate party details (party_type and party fields).

PROBLEM STATEMENT
================================================================================
Current State:
  - ERPNext's standard PayrollEntry creates uniform JV entries for all components
  - Components linked to Receivable/Payable accounts lack party information
  - "Advances" salary component (Receivable type) cannot be reconciled with employees
  - System doesn't differentiate account types during JV creation

Impact:
  - Advance deductions not properly traceable to employees
  - Reconciliation of employee payables complicated
  - Compliance and audit issues

SOLUTION OVERVIEW
================================================================================
Create CustomPayrollEntry class that:
  1. Detects account types (Receivable, Payable, Expense, etc.)
  2. Classifies salary components by their account types
  3. Creates JV entries with party details for Receivable/Payable accounts
  4. Maintains complete backward compatibility with standard components
  5. Uses caching for optimal performance

ARCHITECTURE DESIGN
================================================================================

Class Hierarchy:
  frappe.model.document.Document
      ↓
  hrms.payroll.doctype.payroll_entry.payroll_entry.PayrollEntry
      ↓
  spotledger_hr.controllers.payroll_entry_controller.CustomPayrollEntry

Main Override: make_accrual_jv_entry()

Core Methods to Implement:
  1. get_account_type(account_name) → str
     - Fetch and cache account type
     - Returns: "Receivable", "Payable", "Expense", etc.
  
  2. get_salary_components_by_account_type() → dict
     - Classify all components by account type
     - Returns: {AccountType: [ComponentData], ...}
  
  3. is_party_required_account(account_type) → bool
     - Determine if account needs party details
     - Returns: True for Receivable/Payable/Bank accounts
  
  4. process_party_component(component_data, employee) → list
     - Create JV entry with party details
     - Returns: [EntryDict with party_type and party]
  
  5. process_standard_component(component_data) → list
     - Create standard JV entry (no party)
     - Returns: [EntryDict without party]
  
  6. make_accrual_jv_entry(submitted_salary_slips) [OVERRIDE]
     - Main orchestration method
     - Classifies components → Processes by type → Creates JV

DATA FLOW
================================================================================

Payroll Entry Submitted
        ↓
make_accrual_jv_entry() called
        ↓
get_salary_components_by_account_type()
    ├─ Fetch submitted salary slips
    ├─ Extract all components (earnings + deductions)
    ├─ Get account for each component
    ├─ Get account type (with caching)
    ├─ Group by account type
    └─ Return classified dict
        ↓
For each account type group:
    ├─ Receivable Components
    │   └─ process_party_component(component)
    │       ├─ Create entry dict
    │       ├─ Add party_type = "Employee"
    │       ├─ Add party = employee_id
    │       └─ Return entry list
    │
    ├─ Payable Components
    │   └─ process_party_component(component)
    │       ├─ Create entry dict
    │       ├─ Add party_type = "Employee"
    │       ├─ Add party = employee_id
    │       └─ Return entry list
    │
    └─ Expense/Other Components
        └─ process_standard_component(component)
            ├─ Create entry dict
            ├─ No party details
            └─ Return entry list
        ↓
Combine all entries
        ↓
make_journal_entry()
        ↓
JV Created & Submitted ✓

KEY DESIGN DECISIONS
================================================================================

1. EXTEND vs OVERRIDE WHITELISTED METHODS
   ✓ Decision: Extend PayrollEntry class
   ✓ Reason: Non-invasive, maintains inheritance chain, allows parent calls

2. ACCOUNT TYPE DETECTION
   ✓ Decision: Dynamic detection from Account master
   ✓ Reason: Flexible for future changes, no hardcoding needed

3. PARTY ASSIGNMENT
   ✓ Decision: Always "Employee" for payroll context
   ✓ Reason: Employment relationship context, simplifies logic

4. CACHING STRATEGY
   ✓ Decision: Instance-level cache in _account_type_cache
   ✓ Reason: Eliminates repeated DB queries, good performance

5. ERROR HANDLING
   ✓ Decision: Log warnings, default to "Expense"
   ✓ Reason: Resilient to data issues, prevents JV creation failure

6. BACKWARD COMPATIBILITY
   ✓ Decision: Only override, no parent code modification
   ✓ Reason: Preserves standard functionality, safe rollback

PERFORMANCE ANALYSIS
================================================================================

Complexity: O(m + n)
  - m = number of components
  - n = number of unique accounts

Execution Time (Estimate):
  - Account type lookups: ~50ms (cached after first lookup)
  - Component classification: ~100ms
  - Process components: ~150ms
  - Create JV: ~200ms (standard Frappe)
  - TOTAL: ~500ms acceptable range

Optimization Techniques:
  1. Caching: Account types cached in _account_type_cache
  2. Set-based deduplication: O(1) lookup for duplicates
  3. Single iteration: All components processed once
  4. Lazy initialization: Cache only when needed

ERROR HANDLING & EDGE CASES
================================================================================

Error: Account Type Not Found
  Handling: Log warning, default to "Expense"
  Impact: Low - JV created with safe default

Error: Employee Not Found
  Handling: Throw ValidationError
  Impact: High - Prevents JV, alerts user to data issue

Error: Duplicate Components
  Handling: Skip duplicates using set tracking
  Impact: Low - Ensures accurate totals

Error: Missing Amount
  Handling: Skip entry, don't include in JV
  Impact: Low - Only affects that component

Error: Database Connection Lost
  Handling: Frappe standard error handling
  Impact: High - User alerted, can retry
